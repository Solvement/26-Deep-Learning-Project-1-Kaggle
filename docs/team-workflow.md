# 2–3 人团队研发工作约定

这份约定采用软件与机器学习团队常见的协作流程，适用于功能开发、研究实验、训练和项目交付。默认由每项任务的负责人执行，另一位成员审查；同一人可以兼任多个角色。它是建议采用的团队制度，GitHub 服务端强制规则的启用状态另见文末。

## 角色与权限

| 角色 | 责任 | 小团队安排 |
| --- | --- | --- |
| 项目负责人 | 确定目标、优先级、验收标准、资源预算和交付时间 | 一位成员负责，可按项目轮换 |
| 任务负责人 | 拆分任务、实现或组织实验、记录结果、修复问题 | 每个 Issue 指定一位负责人 |
| 审查人 | 检查代码、测试、实验方法和验收证据 | 由另一位成员承担 |
| 仓库管理员 | 管理成员、分支保护、凭据、自动化和发布权限 | 至少一位；按实际权限需要分配 |
| agent | 按已授权任务写代码、自测、查错、准备 PR 和审查建议 | 在任务负责人的范围和预算内执行 |

成员各用自己的 GitHub/Kaggle 身份。管理员在需要时使用管理权限，日常遵循同一套 PR 规则。agent 不作为独立的人类审批人，也不共享维护者身份。

## 任务从哪里来

每项工作先有一个 GitHub Issue；紧急修复也应在交付前补齐记录。Issue 可以是开发、缺陷、研究、训练或文档任务。使用仓库中的任务/实验模板，写清：

- 目标和验收标准：完成后应观察到什么行为或证据。
- 一位负责人、范围和相关模块；需要并行工作时划分文件边界。
- 已知依赖、规则约束和阻塞；不把未验证的比赛要求写成事实。
- 验证方法；训练任务还包括 GPU/时长预算、数据划分和指标。

GitHub Projects 看板采用 `Backlog → Ready → In progress → Review → Done`，阻塞通过说明或单独标记表达。项目负责人决定什么进入 Ready。每位成员默认只主导一项进行中的任务，任务应足够小，便于尽快审查和集成。

Issue 是工作记录，PR 是代码变更记录；一次纯训练可以只更新实验 Issue 和产物索引，不必为了记录分数创建没有代码改动的 PR。

## 代码如何进入 main

1. 负责人从最新 main 建立短期分支，例如 `feat/12-data-loader`、`fix/19-label-mapping`、`exp/23-augmentation`。
2. 本地或云端开发；提交小而完整的改动，保持其他人的文件和变更完整。
3. 本地验证后推送分支，创建关联 Issue 的 PR；说明结果、实际运行的检查和剩余限制。
4. CI 自动执行适合每次提交的检查；另一位成员审查行为、边界情况、测试和实验方法。agent 可辅助双方。
5. 修复意见后重新运行相关检查；旧 approval 按仓库保护规则失效。
6. 当前提交 CI 通过、必要讨论解决、另一位成员有效批准、分支无冲突且合并已获授权后，squash merge 到 main。
7. Issue 满足验收标准后关闭；成员再同步最新 main，开始下一项任务。

main 是共享、可验证的集成版本。未通过审查的变更留在分支。若 main 出现回归，优先用回退 PR 恢复，再以修复 PR 解决；不重写公共历史来掩盖错误。

## 如何协同处理冲突

同时修改共享模块前，在 Issue/PR 中协调负责人。负责人先读取 main 和对方改动，再合并目标分支、解决冲突并重新测试。agent 可以处理理解明确的文本或代码冲突；涉及两种业务行为、模型方案、数据划分或实验结论时，提出差异和建议，由相关维护者确定取舍。

不得直接选用全部 ours/theirs 来消除冲突，不覆盖他人未提交的工作，不擅自强制推送。两人都可以在本地开发，不需要共享一台开发机。

## CI、训练和交付分别做什么

| 环节 | 触发与目标 | 验收证据 |
| --- | --- | --- |
| CI | 每个 PR 与 main 更新；快速验证代码和依赖 | 当前提交的检查结果与日志 |
| GPU 实验 | 按已授权的实验任务，在选定平台运行 | 可复现记录、指标、日志和模型 |
| 发布/CD | 维护者确认的交付节点；按实际产品执行部署或产物交付 | 版本号、提交 SHA、产物校验和及验证结果 |

当前 CI 是 CPU 环境训练自测。实际训练实现加入后，逐步补充数据读取、标签映射、划分泄漏、模型前后向、恢复检查点、推理和提交格式测试。文档变更无需运行长 GPU 实验。CI 的退出码必须体现失败，不能以空任务或跳过必要检查宣称成功。

长训练不绑定到每次推送。Kaggle、Colab、本地 GPU 使用同一训练代码与配置约定，平台相关的数据挂载和认证留在启动层。探索性实验可在分支固定提交上运行；最终交付应可从已合并的固定提交复现。

## 每次训练必须留下什么

每个实验有唯一记录，关联实验 Issue，并记录：

- 假设、基线、改变的变量和预先选定的评价方法。
- 代码完整提交 SHA；如有未提交改动，记录并在正式复现前提交。
- 配置、随机种子、数据来源/版本或校验和、训练/验证划分和预处理。
- Python/库版本、硬件、运行命令、实际资源消耗与异常。
- 训练/验证指标、最佳检查点选择依据、日志、模型与输出的受控存储位置及校验和。
- 与基线的比较、失败原因或结论；是否值得继续或进入交付。

代码、配置、测试和可公开的结果摘要进入 Git；数据、大模型、密钥和完整训练输出进入符合许可的受控存储。两位成员必须能在相同权限条件下取到交付所需产物。比较模型时固定划分和评价方法；比赛榜单反馈不能代替独立验证。

## agent 与异常处理

负责人给 agent 的任务应包含 Issue、允许修改的范围、验收命令和资源上限。实现 agent 准备分支和 PR，审查 agent 提供发现与依据，CI 排障 agent 根据当前日志诊断和修复；这些职责可由同一工具在不同任务中承担。

无人值守执行需要额外的 GitHub 事件集成和 runner，`AGENTS.md` 本身不会启动后台任务。接入后，每个失败任务最多自动修复并验证两轮，再报告证据和阻塞；只有明确的临时网络/runner 故障才按受控策略重试。不得无限循环、降低断言、绕过校验或扩大权限来获得绿灯。

凭据缺失、比赛规则未知、语义冲突、预算超出和重复失败由负责人处理。自动合并仍受人工 approval 和 required checks 约束。付费资源、外部发布和比赛提交在具体授权范围内执行。

## 项目何时算交付

交付前由负责人和审查人确认验收标准，记录对应 main 提交、版本号及使用说明。软件项目包括必要的部署和恢复验证；本比赛项目包括符合规则的训练/推理代码、复现实验记录、模型、提交文件以及主办方要求的报告/Notebook（具体要求待核对）。

用 GitHub Release/tag 标记被验收的代码版本，关联受控产物与校验和；记录比赛提交文件与实际提交结果，区分未提交、已提交和得分已确认。发布失败时保留记录，按明确的恢复方案处理。

## 日常节奏

每天异步更新任务进展、下一步和阻塞；开新任务前优先处理同伴的待审 PR。每周简短检查目标、看板、失败实验、资源消耗和下周优先级。重要决定写回 Issue、PR 或文档，避免只存在于聊天里。

- GitHub Projects 看板、成员权限、main ruleset、真实 CODEOWNERS、后台 agent、auto-merge、版本发布和训练交付自动化尚未启用。

服务端配置通过 GitHub 仓库界面或恢复访问后的 API 启用，不会因本文件存在而自动生效。main 的建议保护规则见 `collaboration.md`；云端 API 访问问题见 `api-access.md`。
